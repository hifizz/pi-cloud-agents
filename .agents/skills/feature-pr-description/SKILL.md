# 新需求 PR 描述

本项目新需求的 PR 描述默认使用本 skill。参考用户确认的 [PR #27](https://github.com/hifizz/pi-cloud-agents/pull/27) 写法，但以当前代码和验证结果为准，不复制该 PR 的具体实现或测试数字。

目标：前两段让读者知道用途，流程部分让读者知道实现步骤，后续定义让另一个人能够实现或测试同样的行为。像 spec 一样明确，但先讲行为，不要求读者先读完术语表。

## 写之前

1. 阅读需求、实际 diff、调用方和测试证据。更新已有 PR 时先取得当前正文，保留仍有效的信息，不覆盖他人新增内容。
2. 确认 PR 的实际 base、依赖和交付范围。集成分支不等于 main，代码完成不等于部署完成。
3. 选一个无敏感信息的例子贯穿全文。不要在各节更换对象名称。
4. 区分实际类型、说明性伪类型和未来建议。未知行为写“待验证”，不要猜测或用测试总数代替证据。

## 正文模板

保持以下六节的顺序。删掉不适用的子项，必要时用一句“不涉及持久化 / HTTP 接口 / LLM 调用”说明，不为填模板虚构结构。

### 1. 功能定义

用两三句话说明：谁使用、解决什么问题、作用于什么对象、不做什么。

随后简述需求来源、依赖 PR、base 和本次范围。不要以文件清单、提交历史或实现术语开头。

### 2. 一个具体例子

使用一组具体输入，说明操作及预期结果。存在多种状态时用表格比较。

例子帮助理解，不取代后面的完整规则。字段缺失、空字符串、null、禁用、删除等若语义不同，不能混用。

### 3. 主要流程

按实际执行顺序写，每步交代“谁处理、输入什么、输出或副作用是什么”。

- 保存配置、执行任务、恢复任务等不同流程分开描述。
- 说明数据经过哪些组件、接口、传输通道，在哪一步校验、存储、转换或执行。
- 有多条执行路径时说明共同规则与差别，不默认一个入口的验证覆盖其他入口。
- 说明成功响应代表已接收、已保存、已启动还是已完成。

先用普通语言描述流程，具体代码定位放在第 5 节。

### 4. 对象与状态定义

定义业务对象及其标识、归属关系、作用范围。“模型”默认指业务数据模型；涉及 LLM 时单独说明，避免歧义。

建议按需要使用以下表格：

| 对象 | 标识 | 定义 |
|---|---|---|
| 实际对象 | 实际键或 ID | 对象含义及归属 |

| 操作 | 数据或状态变化 | 用户可观察的结果 |
|---|---|---|
| 实际操作 | 新增、更新、删除或不保存 | 明确结果 |

涉及存储时列出位置、表或文件、字段、主键、状态和值的含义。区分持久化状态和运行时计算结果。涉及继承时列出默认、覆盖、清除、例外及不同对象类型的规则。

### 5. 接口与数据格式

列出真实接口，不用“调用相关 API”代替定义。

- HTTP 接口写方法、路径、请求体、响应结构。内部接口或事件写签名、输入、输出。
- 字段注明类型、必填性、默认值；解释缺失、null 和空值。
- 引用实际类型定义；若用 TS 表示 JavaScript 后端对象，明确这是说明性写法，不是源码声明。
- 说明边界校验、权限检查、容量限制、失败结果及已实现的错误码。
- 数据传递注明发送方、接收方、传递内容及是否持久化；敏感数据注明明文出现的位置、加密和脱敏边界。
- 最后用简短的“文件 → 职责”表提供定位，避免逐行讲解源码。

### 6. 生效时机、失败行为与限制

按本需求实际涉及的内容说明：

- 配置或状态何时生效，已有进程或任务是否受影响。
- 失败时是否发生部分操作，重试是否重复执行，重启如何恢复。
- 默认权限与信任边界，明确不提供的保证。
- 用户可见的已知限制：触发动作、实际结果、原因，以及本 PR 是否修复。
- 必要的部署配置、迁移、备份和回滚限制。

当前行为与未来改进分开。把“切面板结束终端”这类生命周期行为写明，不把它误说成保存配置的必要步骤。

### 附录 A：手动验收步骤

保留读者可以照做的流程：前置条件、UI 入口、具体输入或命令、每一步的预期结果、PASS/FAIL 标准及清理方式。

只使用虚构数据，不写密码、token、cookie 或真实连接串。区分临时演示地址与固定产品配置。不把未运行的步骤写成已通过。

### 附录 B：验证证据

记录实际命令及结果、浏览器操作和截图链接。分别标记：

- mock / 参数传递测试。
- 本机真实进程或协议测试。
- 真实外部服务和浏览器验收。
- 用户报告通过的范围。

列明失败、跳过、未验范围及与本功能相关的 warning。多轮修复后使用最终版本的数字，必要时简述证据不足是如何补齐的。不粘贴整段日志或 agent 汇报，不暗示独立审查重跑了父级测试。

## 写法规则

- 直白、具体，一句话表达一条事实或规则。同一对象和动作始终使用同一个名称。
- 每张表的一列只回答一个问题，避免把行为、存储、安全和未来规划混成一格。
- 不用“灵活、健壮、安全、完整支持”等词代替可检验的行为。
- 信息只在一个主要位置完整定义，其他位置简短引用，避免重复堆长。
- 正文可比普通 PR 长，但每段都必须帮助理解或实现。长日志和截图集放链接，不为了形式凑满章节。
- 新需求优先使用本模板，不套用通用工具默认的极短 PR 格式。纯拼写修正等小改动可缩短，不机械展开。

## 发布前检查

- 前两段是否说明用途、不做什么？一个例子是否贯穿全文？
- 保存与执行是否分开？成功、失败、生效时机是否可验证？
- 接口、字段、类型、状态与实际代码是否一致？实际声明和伪类型是否区分？
- 已知限制是否显眼？未来建议是否被误写成已实现？
- 自动化、现场验收和用户反馈是否区分？最终数字、截图和链接是否有效？
- 是否没有真实凭据？是否没有把合并、部署或未运行检查写成完成？

此 skill 规定描述格式，不授予创建 PR、修改代码、合并或部署的额外权限。获得相应授权后才执行操作；更新远端正文后重新读取，确认目标 PR 和内容正确。仅修改描述时不触发无关的完整开发或浏览器验收流程。
