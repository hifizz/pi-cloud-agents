## 约束
- **真实模型只用 SWE-2、GLM 5.3 或 GPT-6.1-sol**（用户 2026-10-25 约定，默认 SWE-2）。GPT-6.1-sol 的网关 ID 尚未核实，要用它之前先查；不要用 Sonnet、GLM Flash 或别的模型。报告里写明每个场景用了哪个模型。
- 只用测试仓库 `hifizz/tars-sandbox-playground`；只创建名称以 `pca-` 开头、带标签 `app:pi-cloud-agents` 的 Sprite，**同时不超过 3 个**；结束时只清理本次验收创建的那些（逐个核对精确名字 + 前缀 + 标签，参考 `scratch/m1-probe-b.mjs` 的 cleanup），不动 `pi-cloud-agents` 和其他 Sprite。
- 开始前 `npm ls @earendil-works/pi-durable` 必须是 1.4.0。
- **用全新的临时 `TARSBOT_DATA_DIR`**（空目录）启动服务，不使用、不修改、不删除真实 `data/`（AGENTS.md 禁止删除 `data/`）。项目是全新开始，不做数据迁移与历史兼容。
- 截图保存到 `docs/acceptance/M1/`，不得出现 token；报告写 `docs/acceptance/M1/README.md`，格式见 AGENTS.md「验收」与需求文档第 8 节（验收编号、版本与环境、前置状态、操作与故障点、预期与实测、证据、后续）。失败不删记录，修复后重跑并写清次数。

## 场景（每条记录 PASS / FAIL / BLOCKED）
1. **新建工作区**：浏览器里选测试仓库与 `main`，输入需求，观察步骤从 `runtime` 走到就绪；Sprite 名字以 `pca-` 开头；Bot 在 `cwd` 里、在 `tarsbot/*` 分支上开始工作。
2. **重复提交**：对话框里连点两次提交（同一 `requestId`）→ 只有 1 个工作区、1 台 Sprite（AC03.1）。
3. **并行隔离**：再建第二个工作区，两个 Bot 各改同名文件（`hello.txt`）→ 内容互不影响（AC03.1）。
4. **初始化中重启**：在 `code` 步骤期间 `kill -9` 服务并重启 → 步骤接续，没有重复 clone（AC03.2）。
5. **长命令 + 强杀**：让 Bot 执行「每 5 秒写一行日志并向计数文件追加一行，共 90 秒」的命令，期间 `kill -9` 服务并重启 → 计数文件只有一行起头的单次执行序列，最终拿到退出码和**完整**日志（包括崩溃前已输出的部分，因为重放从偏移 0 重新给）；**重复 3 次**（AC07.1 / AC07.2，FT03 / FT04 的 M1 版）。另做一次：命令跑完后（有 `exit` 文件）再 `kill -9`，重启后结果被找回、不重跑。
5b. **同一个 `callId` 重复**：让 Bot 连续执行两条不同命令（模型可能复用 `callId`），确认两条各自执行一次、日志不串（探针发现 `callId` 不能做执行编号）。
5c. **`prepare` 与 `start` 之间的窗口**（探针没有覆盖）：用测试钩子或在 Sprite 里手动只执行 `prepare` 后杀服务，重启后工具应显示「结果待确认」而不是自动重启命令。无法在真实环境构造时，如实记 BLOCKED 并说明原因。
6. **取消**：运行中点停止 → 结果显示「已停止」或「停止待确认」，只影响本工作区进程（AC07.3）；同时在另一个工作区跑命令，确认它没被影响。
7. **PR**：让 Bot 推送分支，点「创建 PR」，继续让 Bot 改并再次推送，再点「创建 PR」→ PR 编号不变（AC09.2）。
8. **检查点与重建**：在工作区里制造修改、新增文本、新增二进制、删除各一个文件 → 保存检查点 → 记录每个文件的 sha256 → 把该**测试** Sprite 删除（经 `provider.release`，仅限 `pca-` 受管）→ 点重建 → 逐文件 sha256 与可执行位一致，Bot 仍能继续工作（AC12.1 / AC12.2）。**再加一条**：在重建前让 Bot 开始一条长命令并杀服务，重建完成后重启服务，旧命令在新绑定上显示「结果待确认」，**新 Sprite 上没有出现该命令的 `~/.pca/runs/<id>` 目录**。
9. **全新启动**：空的 `TARSBOT_DATA_DIR` 启动服务 → 页面显示空状态并引导「新建工作区」（没有任何 Bot / 工作区）；创建第一个工作区后，重启服务，工作区、步骤、会话关联、检查点列表都还在。缺少 `SPRITES_TOKEN` 时启动即报明确错误（在另一个临时目录里用临时环境验证，不改真实环境变量）。
10. **密钥泄漏检查**：在 `data/`（含 sqlite 与 WAL）、检查点目录、`logs/`、`docs/acceptance/M1/` 里搜 `GITHUB_TOKEN`、`SPRITES_TOKEN` 的值，0 命中，并做一次假密钥正向对照。

## 通过标准
场景 1–10 全部 PASS（5b、5c 若如实记 BLOCKED 须写明原因并在 M2 补）；第 5 项 3 次全部通过；`docs/M1-PLAN.md` §7 的故障测试已在自动化里完成。M1 完成后据结果重新拆 M2（写锁与人工接管、git 改动面板、审批绑定运行版本、「先出方案」、聊天输入的请求内容冲突检查）及以后。
