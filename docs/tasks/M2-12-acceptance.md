## 场景（每条记录 PASS / FAIL / BLOCKED）
1. **新 Sprite 就绪**：新建工作区后连续让 Bot 执行 20 条 `bash`（简单命令），**没有任何一条**出现「结果待确认」。重建出的新 Sprite 同样做一遍（M2-01）。
2. **同工作区第二个会话**：从工作区 fork 一个可写会话（AC04.1）；A 先写（自动取锁），B 写入得到明确拒绝并提示"可接管"；两者的读不受影响。
3. **接管与围栏（FT-M2-1 的实机版）**：A 在跑一个 60 秒的长命令（每 5 秒写一行日志和计数文件）→ 用户点"接管"→ A 的命令被杀（计数文件不再增长）、A 的结果显示被接管、A 随后的 `write`/`bash` 被拒；用户在工作区里改了一个文件，点"交还"后 Bot 能看到这次真实改动（用改动面板和 Bot 的回答两处印证）。**重复 3 次。**
4. **接管期间的例程**：给工作区建一个每分钟的例程，接管期间不产生写入，交还后恢复。
5. **Git 改动面板（F06）**：让 Bot 用 bash 新增文本、修改、删除、新增二进制、重命名各一个文件，改动面板与 `git status` 一致；展开补丁正确；二进制显示为二进制；超过 200 个文件的场景（可以用脚本造）显示截断提示；面板空闲时不发请求（用网络日志确认）。
6. **审批绑定（FT-M2-2 的实机版）**：Bot 提出一个需要审批的命令（例如 `git push --force` 到测试分支的写法，或 `rm -rf` 一个测试目录），**先不批**；此时对该工作区做一次重建；然后批准——命令**不执行**，结果为审批作废；新 Sprite 上没有该命令的 `~/.pca/runs/<id>`。再做一次无重建的对照：批准后命令正常执行。
7. **先出方案**：新建勾选"先出方案"的工作区，Bot 先给方案、`write`/`edit` 被拦；点"批准方案"后 Bot 开始实施；重复点击批准只产生一条消息。同时验证 `bash` 仍是软约束，界面说明可见。
8. **聊天输入的请求冲突（AC04.2）**：用 curl 以同一 `requestId` 发两条不同内容 → 409 且对话里只有第一条；同内容重发 → 同一个 `submissionId`。界面里正常发送、失败重试的行为不变。
9. **中止文案**：运行中点停止 → 工具结果显示「已停止」；构造 `kill` 无法确认的情况（用假 runner 或在 Sprite 里让进程忽略 TERM/KILL 的变通做法）显示「停止待确认」。无法在真实环境构造的部分如实记 BLOCKED。
10. **全新启动 + 重启保留**：空数据目录启动页面是空状态；创建工作区、取得锁后 `kill -9` 并重启，工作区、锁的持有者与 `epoch`、检查点列表都还在，`epoch` 不回退。
11. **密钥泄漏检查**：在验收数据目录（含 sqlite 与 WAL）、检查点目录、`docs/acceptance/M2/` 里搜 `GITHUB_TOKEN`、`SPRITES_TOKEN`、`TOKEN_ROUTER_API_KEY` 的值，0 命中，并做一次假密钥正向对照；再看一台 Sprite 磁盘上没有令牌样式的内容。

## 通过标准
场景 1~11 全部 PASS（9 若如实记 BLOCKED 须写明原因并说明补测方式）；场景 3 三次全部通过；`docs/M2-PLAN.md` §5 的 FT-M2-1 / 2 / 3 已在自动化里完成且各重复 ≥10 次。完成后据结果拆 M3（预览与交付卡、InstaBox 的 runner 探针、Sprite 内终端 spike 的结论），并更新 M2 的遗留清单。
